# Information Architecture

## Purpose

This document defines what information belongs where in Prompt Architect Studio.

The goal is to keep the app focused: users should understand the product quickly, use the tool immediately, and find supporting context only when they need it.

## Page Priority

The page should prioritize:

1. What the app does.
2. The core prompt-building workflow.
3. Why structured, model-aware prompting matters.
4. Examples and education.
5. Trust and privacy information.

## Recommended Page Structure

### 1. Hero

Purpose:

- Explain the product in one glance.
- Create enough confidence for the user to try the tool.

Content:

- Product name.
- Short headline.
- One-sentence value proposition.
- CTA that anchors to the studio.

Avoid:

- Long explanation.
- Generic AI hype.
- Large visuals that push the tool too far down the page.

### 2. Studio Workspace

Purpose:

- Let the user complete the primary workflow.

Content:

- Rough prompt input.
- Framework selector.
- Target model selector.
- Submit action.
- Copyable output.

This section is the product.

### 3. Framework Context

Purpose:

- Explain the available prompt structures.

Content:

- Dynamic.
- CO-STAR.
- RTF.
- RASC.
- Agentic-Goal.

Design:

- Compact.
- Scannable.
- “Best for” language over theory.

### 4. Why It Matters

Purpose:

- Explain the problem without slowing down first use.

Content:

- Rough prompts hide intent.
- Frameworks reveal structure.
- Different models respond to different instruction styles.

### 5. Example Prompts

Purpose:

- Help users understand what to paste.
- Support hesitant first-time users.

Content:

- Founder example.
- Marketing example.
- Consultant example.
- Internal operator example.

### 6. Trust and Privacy

Purpose:

- Reassure users before they paste context.

Content:

- Do not paste secrets.
- Explain storage/logging stance.
- Explain API processing.

### 7. Footer

Purpose:

- Provide lightweight navigation and project legitimacy.

Content:

- Product name.
- Privacy/trust link or note.
- Future links if needed.

## What Does Not Belong In The MVP

- Full dashboard navigation.
- Account settings.
- Team management.
- Pricing tables.
- Prompt marketplace.
- Long educational articles above the tool.
- Multi-page docs section unless content grows.

## Navigation

MVP navigation should be minimal:

- Product name/logo.
- How it works.
- Frameworks.
- Start.

If the page remains one screen plus supporting sections, anchor links are enough.

## Core Information Rule

If a piece of content does not help the user generate, understand, trust, or copy a better prompt, it should not be on the MVP page.
